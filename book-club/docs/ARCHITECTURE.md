# Архитектура и модель доступа

## Границы хранения

IndexedDB содержит `personal_books`, `personal_reviews`, `reading_progress`, `quotes`, `settings`, `club_catalog_cache`, `sync_queue`. Имя базы включает серверный UUID участника, полученный после проверки Telegram. В обычном браузере — отдельная база `bookclub-local`. Это защита от случайного смешивания аккаунтов, а не шифрование данных устройства. Пользователь с доступом к браузерному профилю может прочитать IndexedDB.

Supabase содержит 16 таблиц из технического задания. Дополнительная закрытая таблица `private.sync_versions` хранит версии применённых публичных операций. Личные заметки, приватные цитаты, отзывы и полные резервные копии никогда не загружаются в Supabase. Запрос внешнего поиска передаёт введённую поисковую строку Google Books/Open Library; загрузка обложки обращается к её HTTPS-источнику.

## Авторизация

1. Frontend получает сырые `Telegram.WebApp.initData`. `initDataUnsafe`, localStorage и выбранный пользователем Telegram ID не доказывают личность.
2. `telegram-auth` проверяет HMAC-SHA256 через Web Crypto, формат, отсутствие дублирующихся параметров и `auth_date`: не старше часа, будущее — не более 30 секунд.
3. Только проверенный Telegram ID сверяется с активным `club_members`. Единственное исключение при первичной настройке — точное совпадение с серверным `INITIAL_ADMIN_TELEGRAM_ID`.
4. Admin API Supabase Auth создаёт/находит служебную учётную запись вида `UUID@telegram.bookclub.invalid`, генерирует и проверяет одноразовый токен на сервере. Это не отправка email; адрес недоставляемый. OTP и refresh token в клиент не возвращаются.
5. Клиент получает обычный подписанный Supabase access JWT. TTL настраивается 600 секунд; токен хранится только в памяти страницы. Продление требует повторно проверить ещё свежие initData. Через час нужно заново открыть Mini App.
6. Edge API вызывает `auth.getUser`, затем заново проверяет активное членство/роль. RLS также проверяет актуальное членство по `auth.uid()`, поэтому отключение действует и на уже выданный JWT.

В Hosted Auth выключите публичную регистрацию и ненужные провайдеры. Не добавляйте пароль/доставляемый email служебным пользователям. Не используйте одновременно другие способы входа в этот же Auth-проект без отдельного анализа привязки аккаунтов.

## RLS и операции

Чтение доступно только активным участникам. `club_members` раскрывает Telegram ID только самому участнику и администратору. Профили видны членам клуба. Участники не могут менять роли ни REST-запросом, ни параметрами Edge API. Администратор назначается серверной конфигурацией; интерфейс приглашает только обычных участников.

Прямые клиентские INSERT/UPDATE/DELETE таблиц запрещены. Изменения идут через Edge Functions и узкие RPC `sync_public`/`club_action`. RPC самостоятельно проверяют `auth.uid()` и роль; обход Edge с прямым RPC не позволяет обойти проверки. Владелец публикации устанавливается сервером. Входной `member_id` игнорируется.

Служебная роль используется только в Edge Auth/worker. Все definer-функции имеют пустой `search_path`, таблицы квалифицированы схемой. Схема `private` не доступна anon/authenticated. Гранты видов явно сбрасываются, включая стандартные Supabase default privileges.

## Приватность

Индивидуальные публикации выключены по умолчанию. Глобальные разрешения также false. Для публикации нужна книга общего каталога и отдельное согласие в локальной записи. Изменения общих параметров книги не переписывают личное издание.

| Данные                | Условия доступа другого участника            |
| --------------------- | -------------------------------------------- |
| Прочитанная книга     | Есть публичная копия книги и `show_finished` |
| Текущая книга         | Есть публичная копия книги и `show_current`  |
| Страницы/общий объём  | Книга видна и `show_progress`                |
| Текст отзыва/спойлеры | Есть публичная копия и `show_reviews`        |
| Оценка                | Есть публичная копия и `show_ratings`        |
| Цитата/комментарий    | Индивидуальная публикация и `show_quotes`    |

Для независимых разрешений колонок используются виды `visible_progress` и `visible_reviews` с явной проверкой членства и настроек. Сырые таблицы прогресса/отзывов не имеют клиентского SELECT. Скрытые страницы/оценки возвращаются как null, скрытый текст как пустая строка. Владелец видит свои загруженные копии для контроля. Каталог не раскрывает локальные книги, которые пользователь не публиковал.

Глобальное отключение скрывает серверные копии без их удаления. Повторное включение может показать ранее явно опубликованные записи. Отключение отдельной публикации отправляет DELETE. Приложение предупреждает, пока изменение приватности или удаление ещё не подтверждено сервером. Уже увиденные/сохранённые другим участником данные отозвать из его независимой локальной копии нельзя.

## Синхронизация

Локальная запись и операция очереди выполняются одной Dexie-транзакцией. При повторном редактировании того же объекта очередь заменяется последним желаемым состоянием. На клиенте один последовательный обработчик; одновременно пришедшее подтверждение не удаляет новую редакцию. Ошибка сохраняет операцию и текст ошибки, повтор выполняется при восстановлении сети, вручную и каждые 30 секунд открытого приложения.

Сервер сериализует операции advisory lock по участнику/типу/UUID. Версия хранится вместе с результатом в транзакции; равная/старая версия не применяется. Удаления оставляют серверную версию, поэтому запоздавшая публикация не воссоздаёт запись. Версия — отметка времени устройства в микросекундном масштабе плюс сохраняемый в IndexedDB монотонный счётчик. Перевод часов назад не уменьшает версию в этой библиотеке. При переносе данных на другое устройство часы должны быть корректны: распределённая синхронизация личных библиотек между устройствами не реализуется. Отключение приватности и удаления обрабатываются раньше обычных публикаций. Полностью приватные записи вообще не создают облачных операций.

Прогресс и отзыв уникальны по `(member_id,book_id)`. Один общий UUID нельзя добавить в одну личную библиотеку дважды. Лайк уникален по `(quote_id,member_id)`. При удалении публичной цитаты лайки удаляются FK cascade. Сохранённая цитата независима: новая локальная запись и `sourceId`, без облачного FK на исходник.

## Встречи и уведомления

Изменение встречи в одной PostgreSQL-транзакции создаёт задания для активных участников и инвалидирует предыдущую версию. Даты хранятся timestamptz (UTC); форма и экран используют часовой пояс устройства. Telegram-текст дополнительно явно указывает МСК.

Cron раз в минуту вызывает защищённую функцию с отдельным секретом из Vault. Worker берёт до 5 заданий через `FOR UPDATE SKIP LOCKED`, назначает lease/token и проверяет версию встречи, активность участника, отмену и отказ от участия. Напоминания после начала встречи пропускаются. При сетевых ошибках — ограниченные повторы; 429 учитывает `retry_after`, 403 считается постоянной ошибкой. Администратор видит задания и может вернуть неудачные в очередь.

Для Telegram нет транзакции, общей с PostgreSQL: если сообщение отправилось, но ответ/запись `sent` потерялись, повтор может отправить дубликат. Изменение встречи во время уже выполняющейся отправки также имеет небольшое окно гонки. Доставка не гарантируется при остановке проекта, блокировке бота, недоступности API или исчерпании квоты. Не используются фиктивные гарантии exactly-once.

## Резервирование

JSON проверяется до изменения базы, максимум 20 МБ. Проверяются схема/версия, уникальные UUID, существование книг у дочерних записей, страницы и оценки. Объединение сохраняет существующие UUID. Полная замена требует отдельного подтверждения и транзакционно создаёт операции удаления прежних публичных копий. Личные записи не публикуются при импорте. Настройки приватности из файла не включают доступ автоматически. Ключи сессии/секреты не экспортируются.
